# 小云手机 App 整体重设计总方案

版本：设计基线 v1.0｜2026-10-25｜状态：待逐页参考图细化，**未授权按本稿直接批量改代码**

阶段说明：用户提供六张新参考图后，首批页面框架以[第一阶段浅色框架确认稿](./2026-10-25_第一阶段浅色框架确认稿.md)为准；本总方案中的深色切换是后续完整目标，第一阶段优先完成全页面浅色，待确认后再动 App 代码。

## 0. 本文档怎么用

这是在**现有 LuminaWatch Android App 上改造**的总设计约束，不是从零新建项目，也不是一组已经实现的功能说明。后续由用户按页面提供参考图、交互提示及优先级；每一页先出页面规格和可核对的视觉稿，经确认再实施。页面级确认稿可以细化本稿的尺寸、布局和色彩，但不得默默删除现有功能、改变数据归属或把演示功能说成真实连接。

优先级：用户新确认的页面要求 ＞ 本文档中已确认的产品规则 ＞ 当前代码中的真实业务能力 ＞ 苹果页面的视觉参考。发生冲突时先列出差异请用户决定，不凭开发者猜测改变方向。过去的「我的手表／表盘图库／发现」三栏、Backdrop/液态玻璃底栏方案**不再是目标架构**；其业务能力要迁移，不能因移除旧入口而丢失。

**核心目标**：将 Apple 健康、健身和 Watch 手机 App 中与小云功能相对应的布局和交互逻辑，整合成一个易懂的三栏 App。视觉上以用户提供的苹果截图／录屏为逐页对照；信息架构、品牌素材和实际能力属于小云。默认浅色，可切深色；不使用液态玻璃。未经用户给出该页参考图并验收，不宣称“一比一复刻完成”。

## 1. 已确认的产品决策

1. 底部**只有三个一级入口：健康｜小云｜手表**。心情、跑步、关怀、表盘、设置等是对应栏目的二级功能，不继续增加底栏项目。
2. 健康首页上方有「所有 Watch ›」，其下显示**当前选中手表的名称与连接状态**，再下方是可编辑的「摘要」，然后是**两列健康类别卡片**。类别和数据详情在本 App 内逐级展开。
3. 同一个 App 将来支持**多只小云手表**。健康页的「所有 Watch ›」和手表页当前设备卡片上的「切换」进入**同一个选择页**；只有一份全局选中设备状态，不摆两个一模一样的顶部按钮。
4. 选中某只表后，健康页及手表页显示该表对应的数据和设置。**切换查看对象 ≠ 建立／断开蓝牙连接**；不能借切换动作伪装配对成功。
5. 没配对时，健康类别及详情入口**仍然存在**；传感器数据区显示无数据和配对引导。本机心情、心理问卷、已有聊天等无需手表的功能仍可进入。
6. 当前手机 App 尚未接入真实手表／后端。可以用**明确标记的演示数据**检验视觉效果；演示数据不能冒充真实测量、同步、设备电量或医疗结论。
7. 新增的**手表跑步记录**纳入「健康 → 运动／跑步」，参考用户提供的 Apple 健身截图处理训练列表、活动详情、进行中与结束状态；真实控制范围必须以手表协议为准。
8. 「小云关怀」保留，作为有来源、可回应的提醒事件；健康侧看记录和结果，手表侧配置规则，必要时进入小云对话，不单独占用底栏。
9. 「手表」承载配对、电量、连接与同步、表盘、闹钟、喝水／久坐等提醒、关怀规则及手表相关设置；**只做设备真实支持的功能**。应用外观和隐私等全局设置可在此有分组入口，但不可让它们看起来是某只表的硬件开关。
10. 小云聊天参考已有云岸 App 的对话体验，但现有本地演示回复与将来的云岸真实服务必须区分。原有心情记录云朵、滑块、三步流程优先保留，做外层排版统一，不为追随苹果而重画核心情绪交互。

## 2. 为什么不能直接照搬苹果三个 App

苹果「健康」负责汇总来自多个来源的数据与健康类别；「健身」提供活动摘要及体能训练；iPhone 上的 Watch App 管理已配对手表及设置。小云把这三类能力放在一个 App，因而**参照各自的页面语法，而不是复制三个独立 App 的底栏或造出三套用户状态**。苹果健康会汇总多来源；我们决定让「当前手表」过滤设备数据，这是小云自己的产品规则，必须在界面明示，不能让用户误以为所有表的数据已合并。[Apple 健康数据来源](https://support.apple.com/zh-cn/104997)、[Apple 健康摘要置顶](https://support.apple.com/zh-cn/guide/iphone/iphe3d379c32/ios)、[Apple Watch 多表管理](https://support.apple.com/zh-cn/guide/watch/apd9a204e8d8/27/watchos/27)、[Apple 健身摘要](https://support.apple.com/zh-cn/guide/iphone/iph4c34a8a95/27/ios/27)。

「一比一」验收对象是用户逐页指定的**信息层级、相对位置、排版密度、导航和反馈**；不能直接使用苹果商标、官方图标或未获授权的表盘资源。小云云朵、表盘与功能名称保留自己的身份。系统状态栏、Android 返回手势、权限弹窗由 Android 平台约束，不伪装成 iOS 系统本身。

## 3. 改造基线：当前有的、要新增的、不能误认的

依据当前 `app/` 代码核对，而非旧 README 中可能过期的描述：

| 能力 | 当前手机 App 状态 | 新设计中的处理 |
|---|---|---|
| 底部导航 | 我的手表／表盘图库／发现 | 改为健康／小云／手表；原页面功能重归属 |
| 设备 | 单个 `WatchDevice`；输入 ID 仅本机保存；无真实 BLE | 新增多设备模型及共用选择页；真实 BLE 另行接入 |
| 健康 | 心率、血氧预览；步数、站立、活动消耗图表为预览 | 统一为设备维度的摘要、类别、详情；真实／演示／无数据分开 |
| 心情 | 三步记录、云朵／滑块、月历、详情、本机持久化 | 归「健康 → 心理健康」，保留记录与月历逻辑 |
| 心理问卷 | 已有 GAD-7／PHQ-9 本地记录页 | 归「健康 → 心理健康 → 心理健康评估」，不塞进心率详情 |
| 小云 | 本地规则回复、会话历史、形象、记忆开关、图片附件 | 小云一级页承载对话；真实云岸接入另行界定 |
| 关怀 | 时间线、分类、详情、回应、回访及偏好 | 健康看事件，手表配规则，对话承接沟通 |
| 闹钟 | 本机列表、编辑、上限 15、删除撤销；未下发手表 | 手表设置内保留；清楚显示「本机保存／待同步」 |
| 表盘 | 三种本机预览主题；可选小云表情素材 | 归手表页；横向浏览、单独编辑，未接入不得显示已下发 |
| 跑步 | 手机 App 尚无跑步记录页；用户说明手表已有新功能 | 作为新功能设计与接入，先做演示记录界面，再接真数据 |
| 喝水提醒 | 手机 App 未发现现成流程 | 设计入口与状态；真实手表提醒须待协议证实 |
| 外观／隐私 | 已有全局深色开关、共享偏好等 | 保留并重新分组；深浅全页面一致 |

保留所有已有本机数据，迁移之前列清字段与兼容方案。旧代码某些路径里仍留有玻璃命名／组件，不代表新版继续采用玻璃样式。既有视觉草稿和 README 不能作为“已接入”的证据。

## 4. 总信息架构与页面层级

```text
首次打开／无设备：欢迎 → 连接手表〔可跳过，进入本机可用功能〕

底栏：健康                      小云                         手表
  ├─ 所有 Watch → 选择／添加表   ├─ 对话／输入／附件            ├─ 当前手表卡 → 同一个选择页
  ├─ 摘要 → 编辑摘要             ├─ 会话历史                    ├─ 连接、电量、同步状态
  ├─ 健康类别（两列）            ├─ 小云形象／个性              ├─ 我的表盘 → 图库／表情编辑
  │   ├─ 心脏 → 心率详情          ├─ 记忆与授权                  ├─ 闹钟
  │   ├─ 血氧 → 血氧详情          └─ 来自关怀的对话上下文        ├─ 喝水、久坐等提醒
  │   ├─ 活动 → 步数／站立／消耗                                ├─ 小云关怀规则
  │   ├─ 运动 → 跑步列表／详情                                  ├─ 手表设备设置
  │   ├─ 心理健康 → 心情记录／月历／问卷                         └─ App 设置 → 外观／隐私／关于
  │   └─ 小云关怀 → 事件时间线／详情
  └─ 指标卡 → 对应同一详情页
```

三栏只承载**一级目的地**；二级页顶部显示返回和具体标题，返回原进入页及原滚动／筛选位置。健康摘要卡与健康类别中的同一指标须落到**同一个详情页**，不能制造两套心率／步数页面。跨栏入口可以存在，但必须清楚显示去向，例如关怀详情的「和小云聊聊」跳到对话并可返回关怀详情。

### 4.1 多手表选择器的唯一状态

| 入口 | 显示方式 | 点后行为 |
|---|---|---|
| 健康首页 | 手表名称上方「所有 Watch ›」 | 进入统一的选择／添加手表页 |
| 手表首页 | 当前设备卡中的名称／「切换」 | 进入**同一页**，不复制第二套按钮／数据 |

选择 B 后，健康指标、跑步记录、设备电量、表盘与闹钟配置均以 B 为对象；切回 A 后恢复 A 的内容。按**人**保存的心情、心理问卷与普通聊天仍属于该用户，不因切换手表消失；由设备触发的关怀事件关联设备并标来源。未绑定时显示「未选择手表」，但不隐藏类别。选中设备 ID 要持久化；删除当前手表后回到明确的未选择态或询问选择另一只，不能悄悄把 B 的数据冠上 A 的名称。

## 5. 三个一级页面的结构和点击合同

### 5.1 健康：首页先认设备，再看摘要，再按类别浏览

纵向顺序：安全区 → `所有 Watch ›` → 当前设备名／连接状态（可显示上次同步时间）→ 页面标题／「摘要」→ 自定义入口 → 置顶摘要卡 → 「健康类别」→ 两列分类卡 → 更多说明。标题和设备块的具体相对尺寸以用户后续截图为准，但**当前设备和数据范围必须始终可理解**。

摘要卡候选：心率、血氧、步数、活动消耗／站立、跑步训练、小云关怀、心情。用户可添加、移除、排序；保留至少一个可见项或给空摘要提示。「编辑」只编辑摘要展示，不删除底层记录，不改变健康类别全集。候选项没有数据时仍可选，卡面显示无数据。卡上的数值、单位、采集时间、来源和状态要在同一视觉区域可读。

类别初稿（后续逐页可细化）：心脏、血氧／呼吸、活动、运动、心理健康、小云关怀；采用两列大圆角分类块，图标、名称和语义色一致。**不摆放小云不支持的健康类别作假入口**。点击类别进入该类的汇总页，进一步点击指标／记录进入详情；类别卡不能直接误跳到无关页面。

### 5.2 小云：对话优先，不把设置挤进主聊天区

一级页主体为当前会话：小云形象与标题、消息列表、固定但不遮挡内容的输入区、附件入口。次级入口是会话历史、形象／聊天风格、记忆管理。沿用现有消息与本地保存能力；与云岸 App 的对话布局和交互对齐要在用户提供对应截图后逐项确认（头像、消息密度、输入栏、历史入口、空状态），**不假定两边已经共用账号或同步**。

如果从关怀事件进入对话，显示本次关怀来源，健康上下文只有在用户授权时才附带；从普通底栏进入不得沿用上一条关怀上下文。图片、发送失败、重试、未接入语音和服务端未连接状态都要可解释。

### 5.3 手表：设备与设置中心，不再承担健康内容导航

顶部是当前手表卡：设备名、型号／标识、配对／连接状态、电量（未知就写「未知」）、上次同步、`切换`。未绑定时同一位置为连接引导，下面的设置结构仍可浏览，需设备支持的操作在详情页给出条件和原因。

内容建议按连续分组组织，而非每个设置都是一张大卡：① 连接与同步；② 我的表盘（手机预览、3 种主题、小云表情／形象）；③ 提醒与日常（闹钟、喝水、久坐、其他已支持提醒）；④ 小云关怀规则与通知；⑤ 手表偏好；⑥ App 设置（外观、隐私、数据与关于）。顶部可搜索**本页设置项**，结果点击仍进原详情。用户后续提供 Watch App 截图后再定每组具体行序和行高；没有设备能力的苹果功能不做空壳开关。

「我的表盘」与「小云形象」分开：前者管理**该设备的表盘预览配置**；后者管理 App 内角色形象。表盘表情可选择「跟随小云形象」或单独指定，横向滑动浏览现有素材。现在选择只更新本机预览，不可写「已同步到手表」。

## 6. 功能页面细则

### 6.1 健康指标详情

通用详情结构：类别返回 → 指标名／数据状态 → 当前或所选日期数值 → 日／周／月趋势 → 指标解释与数据来源。心率、血氧、步数、站立、活动消耗分别用适合数据的图，不为凑布局画假的连续曲线。图表空数据时显示明确空状态；趋势读数与时间范围对应，不能把历史平均写成「此刻」。健康提示不构成诊断。

### 6.2 心理健康：心情和问卷归在一起

路径：`健康 → 心理健康 → 心情／心情月历／心理健康问卷`。心情记录继续保留「当下／今天」选择、情绪滑块、分层小云、描述词、因素、可选备注和保存流程。月历按日期展示云缩略图与同日条数；点日期查看当天条目，并能从该日期补记，保存后返回原日期、立刻看到新记录。日期数字方块需要清楚边界、选中态和记录态，不靠极淡描边区分。描述词与因素按钮可适当增大热区，符合无障碍触控尺寸。

问卷从**心理健康分类**进入，不放在心率／血氧详情尾部。GAD-7、PHQ-9 分开计分，说明结果仅供参考、不是诊断；历史记录与本机存储按当前能力保留。苹果的心境记录在 Watch「正念」和 iPhone「健康」中呈现，相关问卷在 iPhone「健康 → 心理健康」中；这是此分层的参考，而非要求复制其素材。[Apple 心境记录](https://support.apple.com/zh-cn/guide/watch/apd7de0f5610/watchos)、[Apple 心理健康评估](https://support.apple.com/zh-cn/guide/iphone/ipha8d27408f/ios)。

### 6.3 运动／跑步

在健康的「运动」分类中设跑步入口：训练列表（日期、状态、时长、距离等**有来源**字段）→ 单次跑步详情（时间、距离、配速、心率、消耗、分段／路线，**只展示设备实际提供的字段**）→ 可能的进行中／暂停／结束页面。视觉上参考用户发来的 Apple 健身黑底高对比训练截图，但 App 默认浅色主题是否在跑步进行中切为沉浸深色，**留待跑步页参考图确认**；不能因截图是黑底就擅自把全 App 改黑。

目前手机端没有跑步业务实现。第一阶段可用带「演示」标签的可复现跑步样本展示列表与详情；不能让真实用户点「开始」后仅运行手机计时器却暗示手表正在记录。只有手表协议确认支持远程开始、暂停、结束并返回状态后，才启用手机端控制按钮。若手表只能本机发起，手机端仅显示「手表上开始跑步」，收到记录后同步展示。不能凭截图推断现有手表具备路线 GPS、训练圆环或奖章。参考 [Apple 健身训练](https://support.apple.com/zh-cn/guide/iphone/ipha5dddb411/27/ios/27)。

### 6.4 小云关怀与日常提醒

关怀不是独立第四栏。健康首页可置顶「关怀」摘要，健康类别中「小云关怀」进入事件时间线：待回应、类型筛选、事件详情、已回应、稍后回访、与小云聊聊。事件要展示**触发原因、来源、时间及建议动作**；无实际传感器事件时只显示演示样本或空状态，不凭空制造“异常告警”。

手表页的「关怀规则」控制与设备有关的阈值、久坐／喝水等提醒和勿扰时段；全局健康上下文共享在隐私设置中。喝水提醒先定义提醒周期、时段、开关和通知去向；**未有协议／系统通知能力前仅本机预览，不说手表会提醒**。闹钟保存、本机提醒、手表下发三种状态用明确文字区分。设备断开时可编辑草稿，但要显示「待同步」，连接恢复后才确认实际同步结果。

### 6.5 多手表配对与生命周期

首次使用引导：欢迎 → 连接手表／稍后再说。真实配对设计步骤：蓝牙与必要权限说明 → 扫描并列出可识别的**小云设备** → 用户确认设备标识 → 建立连接／身份验证 → 首次同步 → 成功或有原因的失败。设备搜索不到、权限拒绝、超时、断线、重复绑定均有可恢复路径。删除／解绑先说明对本机历史和本机设置的影响，确认后执行；不得直接清除心情、聊天等用户级数据。

这里的「绑定」「蓝牙连接」「数据同步」是三个不同状态；保存一串设备 ID 不能显示为已配对，蓝牙连上也不等于同步完成。当前代码只有本机 ID 绑定演示，真实蓝牙实现需先拿到手表型号、广播标识、GATT 服务／特征、认证、传输及数据格式文档，并用真机验证。多表选择页可先展示**明确标识的演示设备**验证 UI，不得与真实设备列表混在一起无标记。

## 7. 数据归属、空状态与演示数据合同

| 数据／偏好 | 归属 | 切换手表时 |
|---|---|---|
| 心率、血氧、步数、站立、消耗、跑步、设备触发的关怀 | `watchId` + 时间 + 来源 | 切换为目标手表的数据；没有就空状态 |
| 电量、连接、同步、闹钟下发状态、表盘下发配置 | `watchId` | 切换为目标手表状态 |
| 心情、问卷、普通聊天和记忆授权 | 用户／本机账户 | 保留；不因切表改变归属 |
| 摘要卡顺序与全局外观 | 用户偏好 | 默认保持；是否每表单独排序待后续确认 |

每条可视健康值至少有 `设备 ID / 采集时间 / 数据来源 / 是否演示`；没有这些字段不能显示为真实读数。状态矩阵：

| 状态 | 首页与详情表现 | 可操作内容 |
|---|---|---|
| 未配对 | 分类和卡片存在；传感器值显示「暂无数据」，给连接入口 | 心情、问卷、聊天、本机设置可用 |
| 已配对且已连接、有实际样本 | 真实值、测量时间、来源；同步状态独立展示 | 详情与设备操作按能力开启 |
| 已配对但断开 | 留上次真实记录，标「上次测量／同步」和「未连接」 | 历史可看，依赖实时连接的操作禁用或排队 |
| 配对／同步失败 | 保留已有记录，错误原因与重试明确 | 不展示「已连接／已同步」假成功 |
| 演示预览 | 顶层与卡片均标「演示数据」；稳定且可复现 | 可体验页面，不触发真实关怀或医疗结论 |

演示记录与真实记录必须隔离：例如以独立 `Demo` 来源和演示设备 ID 保存，不往真实设备历史里写；一旦真实手表连上，优先显示真实值，演示值不混入同一趋势。演示数值尽量固定，避免刷新后自相矛盾。首次安装时可提供「预览演示界面」入口，用户能够退出演示并看到真实的无数据状态。空状态不是功能消失，且不能简单以 `0` 代替「未知」。

## 8. 视觉系统与交互规范（基线，逐页可校准）

- **主题**：浅色默认，白／浅灰底、实体卡、清晰分隔；深色是完整映射，不是只把底栏换黑。全局开关在「手表 → App 设置 → 外观」；主题持久化，状态栏、弹窗、表单、图表一起切换。无 Backdrop 液态玻璃、折射、放大果冻块和通栏重阴影。
- **底栏**：三项固定、紧凑、不挡内容；图标上文字下，当前项清晰选中。二级详情默认不显示底栏，由顶部返回维持层级；聊天输入等固定元素避开系统手势区。具体高度／选中形状由后续用户参考图定稿，避免再凭想象迭代。
- **版式**：大标题、组标题、连续设置组、摘要卡、分类卡各有固定语义；4/8dp 留白节奏，统一页面边距；信息优先级靠字号、对齐和留白，不靠随意加渐变／毛玻璃。分类卡两列，窄屏文字能换行。
- **颜色**：全局中性色承担结构；心率红、血氧蓝、活动橙／绿、心情情绪色等只作**类别语义**，不用颜色单独表示异常或选中。暗色逐项检查文字、边框和图表对比度。
- **触控**：Android 主要按钮／行有效热区不小于 48dp；可见返回、取消、确认；左右滑动内容（小云表情／表盘）同时有可见选择态，不以手势作为唯一操作。切页与选择提供即时反馈，尊重系统减少动画。
- **图表**：日／周／月数据和单位明确；历史趋势不冒充实时；触点可点选具体值；无数据用解释性占位，不画空的假趋势。数值使用稳定数字排版，状态文字可被读屏识别。
- **语言**：统一「手表」「当前手表」「已连接／未连接」「已同步／待同步」「演示数据」等词，不交替使用语义不同的“绑定成功”“连接成功”。

## 9. 关键交互验收路线

| 路线 | 正确结果 |
|---|---|
| 健康「所有 Watch」→ 选 B → 手表页 | B 的健康数据和 B 的设备设置一致；不意外发起配对 |
| 手表当前设备卡→ 选 A → 健康页 | A 的摘要／趋势出现；B 的数据不串到 A |
| 未配对 → 点心率类别 | 进入心率详情但数值空，能去连接；不跳到手表设置后失去返回路径 |
| 摘要「编辑」→ 添加跑步、移除血氧 | 摘要展示改变；健康类别和底层记录不删除，重启后保留 |
| 心情月历 → 选日期 → 记录 → 保存 | 回到所选日期，数字格与记录列表同步变化，同日多条可见 |
| 心理健康 → 问卷 | 进入问卷本身，不穿过心率／血氧详情；结果明确非诊断 |
| 手表 → 闹钟编辑 → 断开状态下保存 | 显示本机已存／待同步；不显示已在手表生效 |
| 手表跑步 → 运动列表／详情 | 真数据按对应手表显示；演示记录显著标示；手机控制仅在协议支持时出现 |
| 关怀详情 → 授权后与小云聊聊 → 返回 | 聊天显示来源且可返回原事件；普通聊天无残留的关怀上下文 |
| 浅色 ↔ 深色 → 重启 | 所有一级／二级页、弹窗、系统栏主题一致并记住选择 |

## 10. 分阶段工作与每页交付模板

先做信息架构和设计稿，**再**做代码与 APK。每批都以「视觉对照 + 点击路径 + 数据状态」三者通过为交付，而非仅编译通过。

| 阶段 | 范围 | 交付门槛 |
|---|---|---|
| 0：基线与保全 | 当前功能／数据审计、旧新路由映射、启动故障复现、备份／迁移策略 | 无丢失入口和数据；明确哪些是演示 |
| 1：全局骨架 | 三栏、主题、统一二级导航、设备选择状态、通用组件 | 浅／深两套截图；底栏不遮挡、不重复入口 |
| 2：健康主线 | 健康首页、摘要编辑、类别网格、指标详情与空状态 | 选 A/B 数据隔离；未配对入口仍在；每卡点向正确 |
| 3：心理与运动 | 心情／月历／问卷、跑步列表与详情 | 老记录保留；跑步演示与真实边界清楚 |
| 4：小云与关怀 | 对话、历史／记忆、关怀时间线和跳转 | 内容授权与返回栈正确；不伪称云端成功 |
| 5：手表中心 | 多表页、设备状态、配对视觉流程、表盘、闹钟、喝水／久坐、设置 | 设备能力与本机保存区分；无假电量／同步 |
| 6：接入和回归 | 在有协议与真机后接 BLE／云岸；全页面回归与安装包 | 真机连接、断线、恢复、安装启动、数据迁移通过 |

用户逐页给参考图时，页面规格至少写：`参考图与版本`、`目标页面和路径`、`从上到下的模块`、`每个可点击元素的目标`、`浅／深与未配对／断开／演示／真实状态`、`要保留的旧功能`、`不实现的苹果功能`、`截图对照差异`、`验收点击用例`。页面设计稿经用户确认后再进入该页实施；若参考图改变全局规则，先更新本总文档的决策记录。

## 11. 尚待用户逐页或手表协议确定的事项

1. 每一页的精确苹果参考版本、间距、卡片比例、图标与动效；以后续用户图片为准。**本稿不是像素级最终稿**。
2. 跑步记录可取得哪些字段（距离、配速、心率、路线、分段、卡路里），是否能由手机远程启停；未证实前不开放对应控制。
3. 喝水提醒和闹钟到底由手机本地触发、手表本地触发，还是两端同步；必须由固件协议与真实测试决定。
4. 多手表是否允许同时连接、是否有自动切换，以及设备资料迁移／删除策略；本稿只确定**多表管理与当前查看对象**，不假定蓝牙并发能力。
5. 健康摘要的布局尺寸和默认卡片集合、排序是否每表独立；当前先按用户级展示偏好设计。
6. 关怀规则的阈值、通知频率与隐私授权文案；健康风险提醒要经过产品与医疗合规审查，不能从苹果截图直接推断。
7. 云岸 App 对话参考图和后端契约，以及登录／跨设备同步方案；当前手机 App 的本地聊天不是云岸真实会话。

## 12. 本文档的验收底线

三个一级入口固定；所有旧能力找得到且点向正确；多手表只有一份选中状态；用户级与设备级数据不串；未配对不隐藏功能；演示／真实／历史／未知状态不混淆；无液态玻璃；浅深一致；逐页参考图确认；真机安装启动和返回路径通过。上述任一项未验收，不把项目称为“整体重设计完成”。
