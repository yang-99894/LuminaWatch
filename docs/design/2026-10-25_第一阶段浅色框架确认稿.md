## 2. 首批固定架构

```text
底部：          健康                   小云                   手表

健康首页        当前手表范围           小云会话             当前设备／未配对引导
  → 所有 Watch   历史、形象、记忆       → 切换（同一选择器）
  → 摘要编辑                            → 我的表盘
  → 健康类别                            → 连接／同步
  → 各类别／详情                        → 闹钟／喝水／久坐／关怀规则
                                        → App 设置
```

底栏是**紧凑、实体、浅色、三项**，固定在系统手势区之上；无液态玻璃、折射、拖拽放大块。图标和文字都可见，选中态是淡灰实体背景或清晰文字／图标状态，不能出现覆盖最后一行的巨大悬浮胶囊。切到另一个标签后记住原标签滚动位置。所有二级页有明确标题和返回；按返回回到来源位置。

## 3. 三个一级页面的第一阶段线框

### A. 健康（所有状态都保留完整页面）

```text
┌─────────────────────────────┐
│ 所有 Watch  ›               │  → 唯一「选择／添加手表」页
│ 当前设备名                   │  未选时写「未选择手表」
│ 已连接／未连接／演示／上次同步 │
│                             │
│ 健康                         │
│ 摘要                    编辑 │  → 编辑置顶卡
│ ┌──────── 摘要卡 ──────────┐ │  有来源、时间、数值或空态
│ └───────────────────────────┘ │
│ ┌──────── 摘要卡 ──────────┐ │
│ └───────────────────────────┘ │
│                             │
│ 健康类别                     │
│ ┌──────┐ ┌──────┐           │
│ │心脏  │ │血氧  │           │  两列；整卡点击
│ └──────┘ └──────┘           │
│ ┌──────┐ ┌──────┐           │
│ │活动  │ │运动  │           │
│ └──────┘ └──────┘           │
│ ┌──────┐ ┌──────┐           │
│ │心理  │ │关怀  │           │
│ └──────┘ └──────┘           │
├───── 健康 ─ 小云 ─ 手表 ────┤
└─────────────────────────────┘
```

首批推荐摘要默认卡：步数、心率、最近心情／小云关怀（以视觉稿的首屏密度调整），其余作为可选项。**默认卡不等于设备真的有读数**：未配对显示无数据或本机心情；演示模式才展示标注的样本。编辑摘要可选心率、血氧、步数、站立、活动消耗、跑步、心情、关怀等已有／明确规划功能；候选项均能进入同一对应详情。只有实际数据的类别才画趋势。

健康类别有完整入口，即使未配对也不移除；进入后看到对应的说明、空状态和「连接手表」，而不是跳去无关设置页。心情记录和问卷在「心理健康」，关怀时间线在「小云关怀」，跑步在「运动」。

图 6 的大面积留白与单个主按钮适合未配对态，但改成**浅色**、自有设备图、准确文案。若还没有真实 BLE 协议，按钮进入现有「绑定／连接说明」或明确标示的演示流程；**不写「相机配对成功」**。健康和小云底栏仍可访问。已选设备时参照图 1 的层级，但只显示小云支持的设置；不能凭参考图制造「控制中心」「智能叠放」之类假功能。手表页的「切换」与健康页「所有 Watch」打开同一选择器，不构成两套状态。

## 4. 浅色视觉基线与本阶段边界

背景以接近白色／极浅灰为主；卡片白色，设置组为浅灰实体分组；黑色主文字、清晰灰色次文字；适量使用小云强调色和健康类别色。图 2 的柔和彩色背景可作为**局部、极淡的摘要顶部氛围**候选，不把整屏刷成彩虹渐变。图 4、5 的分类块可彩色，但降低饱和度并保证白字／深字可读。图 1 和图 6 的黑色皮肤**只取布局，不取配色**。

本批**所有可见页面先统一浅色**：状态栏、底栏、首页、二级页、编辑页、弹窗和空态不得局部变黑。此前约定的深色切换不取消，但**推迟到浅色全量验收之后**；若现有外观开关仍保留，第一阶段不能出现「点了开关只有部分页面变深」的半成品，实施时需先决定是保留可完整工作的旧深色模式，还是暂时隐藏入口并说明后续恢复。这个取舍实施前必须由用户确认，不能暗中删除用户偏好。

第一阶段不做详情图表精修、跑步手机端远程控制、真实 BLE／后端、苹果无对应的小云功能扩张。演示数据要明确写「演示」；未配对的真实数据写「暂无数据」，电量未知写「未知」。完整功能和旧记录不能因页面搬迁丢失。

## 5. 首批真正动工时的顺序与交付

1. **先保证 App 能启动**，记录当前 APK、设备与崩溃情况，检查现有数据保存路径；不能以模拟器启动代替用户真机可用。
2. 搭三栏新路由、紧凑实体底栏、浅色语义样式、共用页面容器；先保证旧二级功能仍可到达。
3. 搭健康首页骨架、摘要编辑骨架、两列类别骨架；每卡先接对页面，未配对／演示两态都可看。
4. 搭手表页已选／未选两态与唯一设备选择器；保留现有表盘和设置入口。多手表真实数据模型／BLE 另作独立实施，不能用 UI 声称已接通。
5. 小云页移为一级入口，只重排外壳和导航，现有消息逻辑不重写。
6. 交付同一台 Android 设备的三栏长截图、未配对态、编辑摘要页、点击路径清单及可安装 APK；**用户看过骨架后**再逐页提供参考图，进入细节迭代。

第一批通过条件：三个底栏入口及比例对；健康首页有「所有 Watch → 设备名 → 摘要 → 健康类别」完整顺序；手表已配对／未配对两态清晰；编辑摘要能增删排序；任一卡片进正确详情；心情／问卷／聊天／表盘／关怀／闹钟的入口未丢；全可见界面浅色；无玻璃；无假连接或假真实读数。

## 6. 请用户确认的唯一框架级取舍

**深色开关在第一阶段怎么处理？**推荐：先把浅色版做完整、让所有页面可验收；原有全局深色偏好及数据保留，但不把深色列为本批视觉交付。若旧深色在新页面会破坏可读性，则在浅色框架阶段暂时不展示切换入口，等深色整套页面完成后再恢复；在此之前绝不静默清除已保存的偏好。其余框架按本稿先定，具体页面细节由用户后续逐页参考图修订。
